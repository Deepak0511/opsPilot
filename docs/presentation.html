🔒 Bounded-Context Gate

Every request is validated against the Patliputra-Corp systems catalog before any LLM processes it.

How It Works

  1. Extract keywords from user message
  2. Filter through 30+ stop words
  3. Score-match against systems catalog
  4. If ambiguous (>1 match) → LLM refines keywords
  5. Route based on match count

Context Lock

Once a system is matched, subsequent messages reuse the locked context — preventing mid-conversation drift.

Routing Outcomes

1 match→ TRIAGE_MANAGER
2-3 matches→ Clarify (ask user)
0 or >3→ Out of Scope
Pending→ Ticket Confirmation

🔧 Strict Tool Binding Per Manager

Each manager's LLM can only request its authorized tools. The shared ToolNode executor knows all tools, but access is isolated.

ManagerBound Tools
INFRASTRUCTURE_MANAGERsearch_systems, count_systems
KNOWLEDGE_BASE_MANAGERsearch_kb, count_kb_articles
TICKET_READ_MANAGERsearch_ticket_by_id, search_tickets, search_employee, search_systems
TICKET_WRITE_MANAGERsearch_employee, search_systems, search_ticket_by_id, search_tickets, TicketDraft
TRIAGE_MANAGERNo tools — structured output only

⚠️ TICKET_WRITE_MANAGER never directly calls create/update tools. It emits a TicketDraft that the node intercepts.

🤖 Agentic AI Design Patterns

What makes this more than just an API wrapper

🤖 Agentic AI Patterns Used

🧩 Multi-Agent Specialization

5 specialized LLM agents, each with its own system prompt, tool set, and domain boundary. No single "god" agent.

🔄 ReAct Loop

Manager → Tool → Manager → Tool → ... → Final Answer. Each manager can call tools iteratively until it has enough information.

📋 Structured Output

Triage uses with_structured_output(TriageDecision) — the LLM must emit one of exactly 4 Literal values. No free-text routing.

🛡️ Human-in-the-Loop

Ticket mutations require explicit user confirmation. The draft is persisted in state, and a deterministic regex node — not the LLM — parses yes/no.

🔒 Deterministic Gating

The bounded-context gate runs before any LLM, using a scored keyword search. The LLM only refines keywords when ambiguous.

💾 Stateful Conversations

SqliteSaver checkpoints preserve full graph state, ticket drafts, and conversation history across browser refreshes.

⚡ Challenges & Fixes

Problems encountered during development and how I solved them

⚡ Challenge 1 — Keyword Explosion

❌ Before

Naive keyword search on user messages matched hundreds of systems for generic words like "app", "system", "help".

"My app is broken"
→ Matched 47 systems containing "app"
→ Agent confused, hallucinated responses

✅ After

Stop-word filtering (30+ words) + LLM keyword refinement fallback reduces to 1-3 specific matches.

"My app is broken"
→ Stop words removed: "my", "is", "broken"
→ Remaining: "app" → LLM refines → "app"
→ Still ambiguous → ask user to clarify

⚡ Challenge 2 — Guidance vs. Action Misrouting

❌ Before

"How do I raise a reimbursement request?" was classified as TICKET_ACTION_REQUEST by the LLM.

The agent tried to create a ticket instead of explaining the process.

✅ After

Regex guard detects how do I, how can I, what are the steps patterns.

Overrides TICKET_ACTION_REQUEST → INFRASTRUCTURE_LOOKUP_REQUEST with an updated routing reason.

⚡ Challenge 3 — Error Handling Strategy

Decision Record: Tool Error Handling

Option 1: Rely only on ToolNode(handle_tool_errors=True)

Treats all exceptions identically. Sends raw stack traces to the LLM. Risks information leakage.

Option 2: @handle_tool_errors decorator ✅

Differentiates ValueError (user input) from Exception (system error). Sanitizes messages to the LLM while logging full traces for developers.

Result: Two-tier error handling. Validation errors give the LLM actionable feedback ("Employee ID is missing"). System errors return a safe generic message.

⚡ Challenge 4 — WAL/SHM Test Contamination

❌ Before

SQLite's WAL (Write-Ahead Log) and SHM files persisted between test runs.

Previous test data leaked into new runs, causing IntegrityError on duplicate keys and flaky test results.

✅ After

Implemented robust teardown in conftest.py:

  • Session-scoped test DB with fresh schema
  • @pytest.fixture(autouse=True) cleans all 5 tables before every test
  • Separate flush_chat_db.py and flush_ops_db.py scripts
